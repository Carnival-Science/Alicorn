# Issue #104 phase A — material-stream bottleneck record (Windows, 2026-11-22)

Measurement-only record for [issue #104](https://github.com/Carnival-Science/Alicorn/issues/104)
phase A. No renderer path changed in this slice. The question is where rounded
and relief surface cost actually goes, whether high visible-count relief occurs
in dogfood, and whether the phase B instanced-SDF prototype is justified.

## Fixture

`benchmarks/material_stream` builds **one** stream: 500 visible card surfaces
and 28 visible scrolling-row commands. A treatment changes only

- shape: `Rectangle` or uniform rounded radius 8,
- material: `MATERIAL_FLAT` or a registered `Analytic_Relief`
  (bevel width 1, strength 0.42, inner shadow 0.14, outer shadow 0.18,
  radius 3), and
- physical height: 0 or 0.5.

Bounds, clip, opacity, translation, stroke (absent in every treatment), and
painter order are identical. The window form describes the same scene through
`ui.run` (SDL_GPU) and `ui/webgpu.run` (hosted D3D12). The offscreen form
submits the same resolved `Paint_Command` stream through the production
`draw_display_list` path on the real GPU device at 1x, 1.25x, 1.5x, and 2x.

Conditions: cold mount, warm steady, resize sweep, theme change, rapid hover,
scroll, and idle 1.2 s. Conditions with repeated work run 24 passes; cold and
idle run one pass. The window matrix uses five runs per cell; the offscreen
sweep repeats the whole treatment x condition x scale grid five times.

The window path does not fake fractional DPI. Windows exposes one display scale
per monitor, so scales are measured on the same GPU through an offscreen target.
The offscreen fence wait is a GPU completion round trip; it is not
presented-frame latency, GPU execution timestamps, scan-out, or a cross-machine
promise.

The resolved window display list contains 531 commands, of which 528 are the
fixture's cards and rows and three are additional non-fixture commands from the
retained scene. The offscreen stream is exactly 528 commands. The 28-row
viewport realizes 28 rows in every run.

## Counter additions

`native/sdl_gpu` now reports, at host exit and in diagnostics captures:

| Counter | Meaning |
| --- | --- |
| `solid_build_calls`, `solid_build_ns`, `solid_build_p50/p95/p99_ns` | complete solid-stream rebuilds per presented frame |
| `solid_visibility_ns`, `solid_expand_ns` | visibility/clip resolution vs vertex expansion |
| `solid_draw_calls` | actual `DrawGPUPrimitives` calls (one per surface) |
| `solid_commands_considered`, `solid_commands_visible` | stream size and culling |
| `solid_vertex_capacity`, `solid_vertex_capacity_peak` | retained GPU vertex capacity |
| `solid_vertex_growth_events`, `solid_vertex_growth_ns` | first-use buffer replacement |
| `solid_device_idle_waits`, `solid_device_idle_ns` | `WaitForGPUIdle` count/time from growth |
| `solid_vertex_upload_bytes` (existing) | per-frame upload pressure |
| `text_*`, `icon_*`, `image_*` growth and idle counters | the other renderer vertex buffers |

The build-sample ring is bounded at 240 samples, like the diagnostics rings.
The counters are measurement-only and do not change the rebuild/upload policy.

Hosted WebGPU does **not** retain across theme, hover, or scroll changes: vertex
colors and resolved bounds are baked into the mesh, so those conditions rebuild
the same 26.7 MB. Retention is a benefit only for unchanged streams. The native
path additionally lacks the transform buffer that lets the hosted path move
unchanged geometry without rebuilding.

## Where the cost is

- **CPU vertex expansion dominates.** At 1x, rounded relief spends 6.69 ms p50
  (6.98 p95) in `native_solid_build`; visibility/clip is ~0.03 ms. Expansion is
  99.5% of build. Pack is 8.27 ms p50 because text/icon/image prep and upload
  add to the same stage; submit is 0.06 ms.
- **The cost is paid every presented frame on the native path.**
  `native_solid_build` clears and rebuilds the whole solid stream each frame:
  one draw call per visible surface (528-531), and 26.7 MB re-uploaded per
  rounded-relief frame. That is why the issue's 8-13 ms CPU expansion
  reproduces: it is a per-frame full rebuild, not a one-time tessellation.
- **Tessellation, not fill rate or draw-call count, is the steady-state
  bottleneck.** Rounded flat is 1.52 ms build for 324 vertices/surface;
  rounded relief is 6.69 ms for 1404; the near-linear relation is ~9 ns per
  rounded vertex. Draw calls stay at ~528 for every treatment. GPU fence wait
  is 0.68 ms for rounded flat and 2.60 ms for rounded relief at 1x; it grows
  only to 0.74/2.89 ms at 2x, so fill scales far more slowly than expansion.
- **Scale does not multiply rounded tessellation.** 324 and 1404 vertices per
  surface are constant at 1x, 1.25x, 1.5x, and 2x. The scale dimension mostly
  changes fragment cost and the GPU fence wait (rect flat 0.08 -> 0.12 ms;
  rounded relief 2.60 -> 2.89 ms).
- **Buffer pressure is a first-use cost, not a steady-state stall.** The relief
  stream grows the 65,536-vertex buffer to 1,048,576 (37.7 MB) once: 3.2-3.5 ms
  growth including a single 0.10-0.17 ms `WaitForGPUIdle`. After that, no
  growth and no idle stalls; the recurring cost is the 26.7 MB upload.
- **Cold mount adds the growth and warm-up cost.** Rounded-relief cold is
  14.59 ms build p50 vs 6.98 ms warm; the extra is the first-use growth and
  first full-stream page/cache behavior. The idle arm presents once and then
  requests nothing (`idle_after_last_submit_ns` ~1.2 s, zero further
  submissions), so idle is clean.

## Dogfood answer

The representative Scratchpad scene has **no high visible-count relief**:
78 resolved surfaces, 59 rounded, **78 flat, 0 relief, 0 nonzero physical
heights**, plus 40 non-surface commands. The flat Acetate-shaped control scene
has 248 surfaces, 6 rounded, 248 flat, 0 relief.

Real Scratchpad is the same shape in its default appearance:

- default `surface_treatment = .Standard` with the Warm theme; relief geometry
  requires `physical_height != 0`, and Standard supplies zero height even where
  a material ID is analytic;
- Workbench Relief is an explicit appearance choice that maps paper/raised/
  floating to recessed/mounted/floating heights (-1.75 to 2) and rounds
  controls; 15 non-test call sites use `scratchpad_surface_material` and 20
  supply `physical_height=`, so the visible relief count is bounded by visible
  controls (toolbar, tabs, status strip, a few panels/overlays), not by the
  editor rows or a 500-surface scene;
- Acetate's host spike is a flat rectangle scene: four `ui.panel` call sites
  with no material or height, plus two GPU geometry surfaces for the waveform
  and scrollbar. Relief count: zero.

**Dogfood does not exercise high visible-count relief.** The 500-surface relief
case in the issue is synthetic. Even Workbench Relief, the one opt-in relief
appearance, pays for a few dozen control surfaces at 324-1404 vertices each,
not 500.

## Phase B recommendation

Issue #104's adoption gate is at least a 2x p95 rebuild improvement, or at least
75% less vertex storage, without a meaningful GPU p95 regression **on the
measured dogfood workload**.

**Instanced SDF: NO-GO for this slice.** The measured dogfood workload contains
zero visible relief surfaces; the optional Workbench Relief appearance is
bounded to visible controls. There is no end-to-end dogfood workload on which
instanced SDF can demonstrate the required improvement, and the synthetic
500-surface relief case is already dominated by a per-frame native rebuild that
retention would remove more cheaply. Do not start the phase B shader/instanced
prototype on this evidence.

**Native solid retention/transform follow-up: justified, but narrower than the
original hypothesis.** The hosted path's identical-stream encode is 0.40 ms p50
versus 8.83 ms on native (22x), and it uploads the 26.7 MB mesh once. That
quantifies the native per-frame rebuild cost the research predicted. However,
the cross-path table also shows the limit: theme, hover, and scroll changes
rebuild the hosted mesh too (23 rebuilds, 8.3-8.8 ms), because colors and
resolved bounds are baked into vertices. A native retention/transform buffer
would therefore improve unchanged frames and transform-only motion, not color
churn. It is a smaller lever on #169's recorded asymmetry, not a replacement
for the current path, so it is filed as a separate follow-up rather than
implemented here: [#235](https://github.com/Carnival-Science/Alicorn/issues/235).

## Limitations

- One Windows host and one GPU; not a cross-machine promise.
- Host CPU wall time only. No GPU timestamp queries, scan-out, or visible
  latency.
- Offscreen scale runs use an offscreen color target, not a swapchain.
- The window path covers the conditions at the monitor's display scale (1x
  here); fractional scale expansion is covered by the offscreen sweep.
- The resize arm coalesces two descriptions into one presented frame (12 wakes
  and submissions for 24 descriptions), matching the host's corrective-pass
  behavior; it is not a 24-presented-frame per-pass measurement.
- Diagnostics captures and `Frame_Stats` do not include driver or GPU-side
  vertex fetches.
